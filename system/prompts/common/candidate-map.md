# Rolling Knowledge Candidate Map

`reflection/candidate-map.md` 不是 10-reflection 才开始生成的总结表，而是贯穿 01-09 的滚动候选表。

Agent 在学习过程中要持续维护它。10-reflection 的任务不是从零挖掘，而是基于已经积累的候选表查漏补缺、去重、降噪、确认状态，并把少数高价值条目推进到 knowledge-base。

## 什么时候更新

出现以下情况时，检查是否需要更新候选表：

- 用户反复追问某个底层机制，例如 runtime、OS、网络、语言语义、协议、隔离、安全边界。
- demo 实现暴露了新的能力缺口，例如 Rust stream、channel、lifetime、process、TUI event loop。
- 用户做出关键设计取舍、修正错误理解、发现 repo 设计局限或 not-to-copy 边界。
- 源码阅读或测试验证出一个可迁移的不变量、状态机、工程模式或失败处理策略。
- 用户明确说“记录到 candidate-map / 知识候选 / 后面要沉淀”。

如果只是一次性细节、临时代码写法、无迁移价值的错误信息，不要加入候选表。

## 分类

候选表只使用三类，避免越拆越碎：

- `主题核心`：直接回答本 topic 学习目标的核心机制、设计不变量和迁移边界。
- `底层原理`：学习中暴露出的基础机制、通用技术原理、外部最佳实践或反复薄弱点。
- `工程模式`：可复用的模块划分、状态机、测试策略、事件模型、错误处理和协作方式。

不要再拆 `旁路技能`、`基础薄弱点`、`外部对比`、`学习方法` 等并行分类；这些内容需要时归入上面三类。

## 状态

候选状态只能使用：

- `候选中`：进入候选表，但还没有开始认真总结。
- `总结中`：正在被用户解释、复盘、接受 challenge。
- `已归档`：已进入 knowledge-base。
- `已忽略`：确认不值得归档，保留为历史判断。

## 写法

每个候选只保留四列：

```markdown
| 候选 | 为什么值得看 | 证据 | 状态 |
| --- | --- | --- | --- |
```

保持简洁。候选表不是知识库正文，也不是教程；它只负责提醒“哪些点值得在 closeout 和 knowledge-base 阶段认真判断”。

更新时优先追加或修订已有候选，避免重复项。证据可以指向 notes、guides、demo、测试、源码路径、外部资料或用户 closeout。
